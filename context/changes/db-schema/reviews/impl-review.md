### F1 — set_updated_at() rollback drops a shared function unsafely

- **Severity**: ⚠️ WARNING
- **Impact**: 🔎 MEDIUM — real tradeoff; pause to reason through it
- **Dimension**: Safety & Quality
- **Location**: supabase/migrations/20260530000001_create_dogs.sql:40–63
- **Detail**: `set_updated_at()` is created with a generic name via `CREATE OR REPLACE FUNCTION`. Future migrations will likely reuse it for other tables' updated_at triggers. The rollback comment contains `DROP FUNCTION IF EXISTS set_updated_at()` — if followed, it silently destroys any trigger on any table that calls this function. The function's generic name implies shared-utility intent, but the rollback treats it as table-local.
- **Fix A ⭐ Recommended**: Remove the function drop from the dogs rollback comment; add a note that it is a shared utility dropped only when no tables reference it.
  - Strength: Safe for partial rollback; documents the shared nature explicitly.
  - Tradeoff: Rollback comment is slightly incomplete as a standalone script.
  - Confidence: HIGH — function is already named generically; shared-utility intent is clear.
  - Blind spot: None significant.
- **Fix B**: Rename to dogs_set_updated_at() and replicate per table.
  - Strength: Each migration is fully self-contained.
  - Tradeoff: Pure duplication — identical function bodies per table.
  - Confidence: LOW — against the plan's intent of a reusable trigger.
  - Blind spot: None significant.
- **Decision**: FIXED via Fix A — removed unconditional `DROP FUNCTION` from rollback; replaced with guarded note explaining shared-utility nature.

### F2 — training_logs: no constraint enforcing element_id→dog_id consistency

- **Severity**: ⚠️ WARNING
- **Impact**: 🔎 MEDIUM — real tradeoff; pause to reason through it
- **Dimension**: Safety & Quality
- **Location**: supabase/migrations/20260530000003_create_training_logs.sql:30–39
- **Detail**: `training_logs` holds both `element_id` (FK → training_elements) and `dog_id` (FK → dogs). Nothing at the DB level verifies that the element belongs to the dog. A buggy client could INSERT a log row where element_id is from dog A but dog_id is dog B — both FKs satisfy, the INSERT RLS policy passes (checks account ownership only), and the row commits with inconsistent data. The highlight algorithm queries by (account_id, dog_id, trained_on) — mismatched rows would silently corrupt per-dog training counts.
- **Fix A ⭐ Recommended**: Add a consistency clause to the INSERT policy's WITH CHECK:

  ```sql
  AND EXISTS (
    SELECT 1 FROM training_elements
    WHERE training_elements.id = element_id
      AND training_elements.dog_id = dog_id
  )
  ```

  - Strength: Closes the gap at the DB layer; zero schema change needed.
  - Tradeoff: Adds one subquery to INSERT RLS — negligible for write-path ops.
  - Confidence: HIGH — narrow and additive fix.
  - Blind spot: Policy edit requires a new migration.

- **Fix B**: Enforce at application layer only (document the invariant).
  - Strength: No migration needed now; deferred to S-02/S-03 service layer.
  - Tradeoff: DB remains inconsistency-permissive; a future service bug could silently corrupt training counts.
  - Confidence: MEDIUM — depends on strict service-layer discipline indefinitely.
  - Blind spot: Haven't surveyed the S-02/S-03 plan to know how strictly inserts are centralised.
- **Decision**: FIXED via Fix A — added `AND EXISTS (SELECT 1 FROM training_elements WHERE training_elements.id = element_id AND training_elements.dog_id = dog_id)` to INSERT policy WITH CHECK.

### F3 — NewDog silently omits account_id (NOT NULL); latent insert failure

- **Severity**: ⚠️ WARNING
- **Impact**: 🔎 MEDIUM — real tradeoff; pause to reason through it
- **Dimension**: Pattern Consistency
- **Location**: src/types.ts:39
- **Detail**: `NewDog = Pick<Dog, "name">` omits `account_id`, which is NOT NULL in the schema. The JSDoc comment says "`id`, `created_at`, and `updated_at` are generated by the database" — but says nothing about `account_id`. A service function constructing a `NewDog` and passing it to `.insert()` gets a NOT NULL violation at runtime with no compile-time warning. The intent is presumably that the service layer injects `account_id` from the session, but this is undocumented and unintuitive to future S-02 implementers.
- **Fix A ⭐ Recommended**: Include account_id in NewDog and update the comment:

  ```typescript
  /** Insert payload for dogs. `id`, `created_at`, `updated_at`
   *  are generated by the database. `account_id` must be set to
   *  the authenticated user's id (from the session). */
  export type NewDog = Pick<Dog, "name" | "account_id">;
  ```

  - Strength: TypeScript enforces that callers pass account_id; omission caught at compile time.
  - Tradeoff: Service layer must thread account_id through (it does anyway — this makes it explicit).
  - Confidence: HIGH — standard Supabase pattern for user-scoped rows.
  - Blind spot: None significant.

- **Fix B**: Keep omission, add a JSDoc note explaining the injection pattern:

  ```typescript
  /** `account_id` is injected server-side from the session;
   *  do not include in client-provided data. */
  export type NewDog = Pick<Dog, "name">;
  ```

  - Strength: No type change; service layer still injects freely.
  - Tradeoff: Type remains incomplete; compiler cannot warn on omission.
  - Confidence: MEDIUM — documentation-only; relies on future implementers reading the comment.
  - Blind spot: Whether S-02 centralises all dog inserts or not.

- **Decision**: DEFERRED — noted in roadmap.md S-02 implementation notes. Must be resolved before S-02 ships any dog-insert code.

### F5 — training_elements RLS silently depends on dogs RLS staying active

- **Severity**: 👁 OBSERVATION
- **Impact**: 🏃 LOW — quick decision; fix is obvious and narrowly scoped
- **Dimension**: Architecture
- **Location**: supabase/migrations/20260530000002_create_training_elements.sql:22–55
- **Detail**: All four training_elements policies use an EXISTS subquery on dogs. The ownership check works because dogs SELECT RLS is enforced during the subquery. If dogs RLS were disabled (e.g., in an admin session or future migration), the subquery widens to all dogs and leaks cross-account element access. This is an undocumented layered trust dependency.
- **Fix**: Add a brief inline comment in the migration noting this dependency: `-- NB: ownership check relies on dogs RLS being active`.
- **Decision**: PENDING
