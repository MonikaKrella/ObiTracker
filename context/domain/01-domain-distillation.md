# ObiTracker — Domain Distillation

## Step 0 — Project context

**Requirements documents found** (all present, so no README-only fallback was needed):

- `context/foundation/prd.md` — locked PRD (frontmatter: `status: draft`, `context_type: greenfield`, created 2026-05-23).
- `context/foundation/tech-stack.md` — starter/stack rationale.
- `context/foundation/shape-notes.md`, `context/foundation/roadmap.md`, `context/foundation/lessons.md` — supporting foundation docs.
- `context/archive/**` — one archived `change.md` + `plan.md` (+ `research.md` where present) per shipped change. These are the **narrative/change history** and turned out to carry the most domain nuance — especially `context/archive/2026-06-17-training-grid/research.md`, which documents five successive corrections to the highlight algorithm, and `context/archive/2026-06-23-testing-highlight-correctness-recalculation-wiring/`, a dedicated bug-fix change for that same algorithm.

**Stack / layering** (from `tech-stack.md` and repo inspection): Astro 6 SSR app (`output: "server"`), React 19 islands for interactivity, Supabase (Postgres + Auth) for persistence, deployed to Cloudflare Workers.

- **Persistence / invariant layer**: `supabase/migrations/*.sql` — table constraints, RLS policies, `SECURITY DEFINER` RPCs. This is where several invariants are actually enforced (see Step 3).
- **Service layer**: `src/lib/services/*.ts` (`dogs.ts`, `training-elements.ts`, `training-logs.ts`) — one file per aggregate, thin wrappers over the Supabase client.
- **Pure domain logic**: `src/lib/highlight.ts` (the highlight algorithm), `src/lib/dates.ts` (window math), `src/lib/training-grid-helpers.ts` (tick-map/tick-count shaping). These are the only files with a dedicated test suite (`highlight.test.ts`, per `plan.md`'s explicit test-suite exception).
- **API layer**: `src/pages/api/**/*.ts` — Zod validation, auth/ownership checks, calls into services.
- **UI layer**: `src/components/**`, `src/pages/**/*.astro` — Astro pages (SSR) + React islands (`client:load`/`client:only`).
- **Shared types**: `src/types.ts` — entity + insert-DTO interfaces, explicitly documented as mirroring the DB schema 1:1.

## Step 3 — Candidate aggregates and invariants

### Aggregate: `Dog`

- **Invariant**: A dog belongs to exactly one account and is only ever visible to that account.
  - Source: `prd.md:110-112` (Access Control: "All data belongs to that account only").
  - Status: **Enforced** — RLS policies on `dogs` scope every operation to `(select auth.uid()) = account_id` (`20260530000001_create_dogs.sql:18-33`), tightened for soft-delete in `20260531000001:13-15`. `anon` SELECT is explicitly revoked (`:37`).
- **Invariant**: A soft-deleted dog is invisible to the handler and cannot be un-deleted or re-selected.
  - Source: NOT in `prd.md` — this invariant exists only in code/migrations, not in the PRD.
  - Status: **Enforced** — `is_deleted = FALSE` baked into the SELECT RLS policy itself (`20260531000001_dogs_soft_delete.sql:13-15`), so even a raw query cannot see deleted rows; `getDogById`/`getDogsList` additionally filter `is_deleted = false` at the application layer (`src/lib/services/dogs.ts:8-29`, belt-and-suspenders).
- **Invariant (candidate)**: A handler cannot have two live dogs with the same name (case-insensitive).
  - Source: NOT in `prd.md` — FR-002 only says "Handler can add a dog with a name," no uniqueness requirement stated anywhere in the PRD.
  - Status: **Declared in application code only, not DB-enforced** — `isDogNameTaken()` (`src/lib/services/dogs.ts:35-47`) is a check-then-insert in `src/pages/api/dog/index.ts:33-38`, with no unique constraint or index on `dogs.name` in any migration. This is a race condition: two concurrent requests can both pass the check and insert duplicate names. Contrast with `training_elements`, which has a real DB-level `UNIQUE (dog_id, name)` constraint (`20260530000002_create_training_elements.sql:11`).

### Aggregate: `TrainingElement` (child of `Dog`)

- **Invariant**: An element's name is unique within its dog (case-insensitive), and this is true even under concurrent writes.
  - Source: NOT in `prd.md` — FR-004 doesn't mention uniqueness.
  - Status: **Enforced at the DB level** — `CONSTRAINT training_elements_dog_id_name_unique UNIQUE (dog_id, name)` (`20260530000002_create_training_elements.sql:11`). Note: the constraint is byte-exact unique, while the app-level `isElementNameTaken()` check is case-insensitive (`ilike`, `src/lib/services/training-elements.ts:31-52`) — a plausible edge case ("Heel" vs "heel") would pass the app check's rejection but is not what the DB constraint alone would block, meaning the two layers aren't perfectly aligned (the app check is the actual case-insensitive gate; the DB constraint is a weaker backstop for exact duplicates and race conditions).
- **Invariant**: `sort_position` determines a deterministic per-dog display order.
  - Source: NOT in `prd.md`.
  - Status: **Enforced procedurally** — `createTrainingElement` always computes `MAX(sort_position)+1` for the dog rather than trusting the column default (`src/lib/services/training-elements.ts:59-89`, comment at `:54-58`); `reorder_training_elements()` RPC rewrites all positions atomically from a caller-supplied full ordering (`20260610000001_reorder_training_elements_fn.sql:13-23`).
- **Invariant**: Deleting an element deletes its entire tick history (no orphaned logs).
  - Source: NOT in `prd.md`.
  - Status: **Enforced at the DB level** — `training_logs.element_id` has `ON DELETE CASCADE` (`20260530000003_create_training_logs.sql:13`), documented explicitly in `deleteTrainingElement()`'s docstring (`src/lib/services/training-elements.ts:117-122`).

### Aggregate: `TrainingLog` (tick record; conceptually owned by `Dog` via `TrainingElement`)

- **Invariant**: At most one log row per `(element, day)` — a day is either ticked or not, never double-counted.
  - Source: `prd.md:118` ("the grid records presence only (tick/untick)"); implied by FR-006 (`prd.md:91-93`).
  - Status: **Enforced at the DB level** — `CONSTRAINT training_logs_element_id_trained_on_unique UNIQUE (element_id, trained_on)` (`20260530000003_create_training_logs.sql:17`), and the toggle service relies on this constraint's `23505` violation as the actual tick/untick decision mechanism (`toggleTrainingLog`, `src/lib/services/training-logs.ts:40-75`).
- **Invariant**: A tick can be logged for the cell's day (today or any past visible day), never a future day.
  - Source: `prd.md:91-93` (FR-006: "the tick records the day of the cell, not the day of entry").
  - Status: **Enforced at the API boundary only** — `isFutureUtcDate()` guard in the Zod schema (`src/pages/api/dog/[id]/logs/index.ts:13-17`, `src/lib/dates.ts:44-47`). Not enforced at the DB level (no `CHECK (trained_on <= CURRENT_DATE)` constraint) — a direct RPC/SQL write could violate it.
- **Invariant**: A log row's `element_id` must actually belong to the `dog_id` it's filed under (no cross-dog corruption).
  - Source: NOT in `prd.md`.
  - Status: **Enforced twice, redundantly** — RLS `WITH CHECK` clause on INSERT re-derives ownership via an `EXISTS` join from `training_elements` to `dog_id` (`20260530000003_create_training_logs.sql:42-46`, comment at `:29-32`); the API layer independently calls `elementBelongsToDog()` before writing (`src/pages/api/dog/[id]/logs/index.ts:49-52`, docstring in `src/lib/services/training-elements.ts:141-148` calling this "defense in depth").
- **Invariant**: A log row belongs to exactly one account, matching the session's authenticated user.
  - Source: `prd.md:110-112`.
  - Status: **Enforced** — RLS on all three operations (`20260530000003_create_training_logs.sql:25-51`); `account_id` is always sourced server-side from the session, never from request body (comment `src/lib/services/training-logs.ts:37-38`).

### Aggregate/computation: `Highlight` (derived, not persisted)

- **Invariant**: Highlighting only fires when there's a genuine outlier signal — no highlight at all below a data-density threshold (`n ≤ 3`), single-winner-only in the mid-range (`4 ≤ n ≤ 6`), full top-3/bottom-3 at `n ≥ 7`.
  - Source: **NOT in `prd.md`.** The PRD states one flat rule (`prd.md:95-96`, `104-108`): top-3 green / bottom-3 red, tie-expand at rank 1 only. The three-tier structure exists exclusively in `research.md` (Corrections 1–5, `context/archive/2026-06-17-training-grid/research.md:882-914`) as a post-hoc refinement never folded back into the PRD.
  - Status: **Enforced in code**, exactly as re-derived through five corrections — `computeHighlights()` (`src/lib/highlight.ts:50-151`).
- **Invariant**: A highlighted set that covers half or more of all elements is meaningless and must be suppressed.
  - Source: NOT in `prd.md` at all.
  - Status: **Enforced in code** — `greenSet.size * 2 >= n` / `redSet.size * 2 >= n` post-build suppression (`src/lib/highlight.ts:113-117, 140-144`).
- **Invariant**: Rank 2/3 (and their red mirrors) must never arbitrarily promote one element out of a tied group.
  - Source: NOT in `prd.md`; discovered via a production-adjacent bug report during manual testing (`research.md:910`, "Correction 5... found via manual testing").
  - Status: **Enforced in code** — `countFrequency.get(...) === 1` uniqueness guard (`src/lib/highlight.ts:104, 109, 131, 136`).

## Step 5 — Refactor ranking

Ranked by **value** (how load-bearing the invariant is to the product's stated success criteria) × **risk** (how poorly today's enforcement matches the documented — or undocumented — intent):

1. **`computeHighlights` / highlight algorithm — #1 priority.**
   Value: maximal — it _is_ the Primary success criterion (`prd.md:38`) and the one thing the Vision names as the differentiator (`prd.md:22-24`). Risk: highest in the codebase — the PRD (`status: draft`, never updated) describes a materially simpler rule than what ships; five undocumented-in-PRD corrections have already been needed post-launch (one of them, Correction 5, was a real production-adjacent bug involving arbitrary tie promotion); and crossover #1 (window-agnostic vs. window-scoped ranking) is a live, unresolved contradiction between what the PRD's Business Logic section promises and what a handler actually sees. Any handler-visible bug here directly undermines the "under 10 seconds, no reading" success criterion — and the PRD is currently useless as a spec to catch regressions, since it doesn't describe the tiers, the suppression rule, or the window-agnostic behavior at all. **Recommendation: reconcile `prd.md` FR-007/Business Logic with the actual Tier 1/2/3 + suppression algorithm, and explicitly resolve whether ranking should be window-scoped or window-agnostic — that decision currently exists only as a comment and a plan.md line, not as a ratified product decision.**

2. **`Dog` name uniqueness.**
   Value: moderate — not a stated requirement at all, but if it's an intended invariant (the app clearly believes it is, given the dedicated `isDogNameTaken` check and 409 response), it protects the handler's ability to unambiguously select a dog in `DogSwitcher`. Risk: real but narrow — it's enforced with a check-then-insert race (`src/lib/services/dogs.ts:35-47` → `src/pages/api/dog/index.ts:33-38`) with no DB-level backstop, unlike the equivalent `TrainingElement` invariant which _does_ have a DB constraint. Low likelihood of concurrent duplicate-name submissions for a solo, small-scale app, but the fix (a `UNIQUE (account_id, lower(name)) WHERE is_deleted = false` index) is cheap relative to the inconsistency it removes.

3. **`TrainingLog` future-date guard.**
   Value: moderate — protects FR-006's "records the day of the cell" semantics (`prd.md:91-93`) from a corrupted grid (a tick appearing in a column that hasn't happened yet). Risk: low — only reachable via a direct RPC call bypassing the API's Zod validation, which requires already having valid, authenticated database credentials; the RLS/ownership boundary is the real security perimeter and is intact. Enforcement is currently API-only (`src/lib/dates.ts:44-47`), not DB-level.

4. **Soft-delete / reorder / uniqueness features shipped without a corresponding FR (crossovers #3-5).**
   Value: low-to-moderate individually, but collectively they represent scope drift the PRD doesn't track — a future reader of `prd.md` alone would not know these features exist. Risk: low from a correctness standpoint (each is well-tested per its own archived change), but non-zero from a _documentation_ standpoint: the PRD is the source of truth referenced by `CLAUDE.md` and future planning skills (`/10x-plan`, `/10x-frame`), and its silent gaps here make it progressively less trustworthy as scope grows.
